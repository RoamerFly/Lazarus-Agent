# F01 答辩提纲

## 三分钟演示顺序

1. 说明维护人员手里只有旧 APK、目标设备和操作规程。以自有离线巡检单模拟旧工具换新平板，指出原包无法默认安装，且原功能不能记住上次路线。
2. 在工作台选择 Android 16，在对话提出恢复安装及记住路线的需求。打开提交前固定的多步验收，让评审看到南北线切换和两次冷启动的要求。
3. 展示一段实际模型工具轨迹。搜索和阅读定位位置，改动 smali 及资源，回编、签名、安装并按界面测试。时间较长时使用有节选标记的录制片段。
4. 展示独立验收报告及导出的 APK。解释原包、候选、设备回读的哈希如何对应，并选择一个失败轮次说明为什么没有交付。
5. 展示跨应用结果与三类对照，最后给出独立 Windows 复测入口和当前未完成的交付项。

演示使用的结果以该批次报告为准。固定评测的失败轮次及暂停中断均在预设分母内。后续修正的回归试验在另批记录。

## 常见问题与回答依据

| 问题 | 回答与应展示的证据 |
|---|---|
| 自研的核心是什么 | 展示受限工作区、需求编排、精确编辑校验、候选版本关系、独立行为执行与下载门禁。Apktool 等工具和外部模型的作用分别说明。 |
| 能处理未内置的新需求吗 | 展示模型阅读实际包内代码后新增持久化逻辑，以及资源改造和分享故障用例。通用工具包括文件搜索、方法读取、精确修改、新建文件和构建；实现结果由实际验收决定。 |
| 为什么要有独立验收 | 展示模型自己声明完成但候选未通过预期操作的记录。验收器使用提交时固定的步骤、目标应用控件及真实设备安装哈希。 |
| 怎么看重复性 | P1B 正例 16/18，巡检单 2/3，独立留出雨伞样本 3/3。展示每项用例的三轮结果和全部分母。同模型一次构建对照 6/6，多轮流程的相对增益仍待验证。 |
| 自动通过就等于需求全部实现吗 | 固定步骤只覆盖已经指定和可观察的行为。还要检查代码差异、保留的数据和业务流程。界面结果无法覆盖的部分应补充验收或人工复核。 |
| 一定要在线模型吗 | 本地规则及已生成候选的复测可在准备好环境后离线运行。开放需求的自主分析与代码生成需要配置模型服务。 |
| 模型调用成本是多少 | 展示实际响应中的缓存命中、未命中和输出量，以及用时。按当时定价估算，缺少计量的部分留空，首次环境下载与本地存储另计。 |
| 能在评审电脑重新做吗 | 先用发布安装器，再按指南准备目标环境，执行同一基准、候选和报告的复测。展示全新 Windows 的安装、首次准备及行为报告，非开发者试用另附实际反馈。 |
| 修复后能覆盖原安装吗 | 取决于签名证书。重签候选与原证书不同会有升级冲突，复测在专用环境全新安装。业务环境需要保全数据，并按其签名和迁移条件决定交付方式。 |
| 所有旧 APK 都能改吗 | 缺目标架构原生库、停服后台、加密或无法分析的逻辑可能无法完成。展示 MIPS-only 样本和其他失败，而不是外推普遍成功率。 |
| 是否已有企业试点 | 当前主案例是合成巡检场景。展示真实历史应用旁证与拟定试点流程，实际业务收益以未来授权现场对照为准。 |
| 单人团队如何实施 | 由刘飞扬负责需求、验收、工具集成与材料，使用 AI 辅助实现，基础依赖公开列出。后续试点需要业务人员与独立复核参与。 |
